# 00. 锚点：Xiao LSP 的规矩与技术前提

> **这份文档不是规划，是锚点。** 它只做两件事：**立规矩**、**记已知前提**。
> 具体怎么做、分几批、先做哪个 method——**留待专项规划**，本文件刻意不冻结那些。
>
> **写给谁**：接手 LSP 专项规划的那个 Agent。**动笔规划前先读完本文**。
> 本文里标「**已核实**」的，是有人实际读过代码/查过规范得出的；
> 标「**待定**」的，是刻意留给专项讨论的，**不要在本仓的实现里偷偷定下来**。

## 一、这是什么仓

**Xiao 语言的 Language Server，单开仓库。**

- **主仓**：`D:\project\Xiao\Xiao`（Rust 核心 + TypeScript CLI，本文中称「主仓」）。
- **本仓**：`D:\project\Xiao\LSP`，**主仓的下游消费者**。
- **技术栈**：**Rust 打底**（`.gitignore` 已是 Cargo 模板）。

**⚠️ 关系是单向的**：本仓**依赖**主仓的语义能力，**主仓不依赖本仓**。
任何"为了让 LSP 好用，去改主仓的语义"的想法，**都要先走主仓的冻结流程**，不能在本仓顺手改。

## 二、规矩

### 2.1 不得实现第二套 Xiao 语义（**最硬的一条**）

主仓 `00-decisions` 已冻结：**TypeScript 层只负责命令、配置、终端交互和进程/库边界，
不实现第二套 Xiao 词法、类型、字节码或运行时语义。**

**本仓沿用同一条**：LSP 只做**协议适配、位置换算、索引与缓存**。
词法、语法、类型、模块解析的**唯一来源是主仓**。

**⚠️ 具体含义**：

- **不得**在 LSP 里重写一遍 Xiao 的解析器/类型检查器（哪怕"只是简化版"）；
- **不得**在 LSP 里维护一份自己的"Xiao 语法表"或"保留字表"；
- 遇到主仓**没有**暴露的能力，**要么扩主仓的接口，要么登记缺口**——
  **不自己补一个近似实现**。近似实现会漂移，而漂移的 LSP 比没有 LSP 更糟。

### 2.2 文档先行

主仓的节奏是**先冻结、再实现、后验收**。本仓沿用：

- 动一个 method 之前，**先写清它的语义、边界和降级行为**；
- **未决决策不得通过临时实现偷偷冻结**；
- 每个交付批次有**明确的退出条件**，验收以实测为准，**不以"提交信息里写了验证"为准**。

### 2.3 单一来源，引用而非复制

Xiao 的规则（颜色、位置口径、诊断码含义）**在主仓**。
本仓要引用时，**写明来源与版本**，**不要把规则抄一份过来**——
主仓改一次，抄来的那份就漂移了。这是主仓的头号病史，**不要在新仓重演**。

### 2.4 不静默降级，能力要显式声明

LSP 的 `capabilities` 就是干这个的：**不支持的 method 不要注册**。
主仓在终端侧已确立同样的原则（无法上报的组合键**静默无反应且不报错**，
而不是猜一个动作）。**能就是能，不能就是不能**，不要用近似行为糊过去。

## 三、注意事项（已核实的技术前提）

### 3.1 位置编码：**UTF-16 是底线，绕不开**

**已核实**（读过主仓 `core/rust/crates/xiao-source/src/lib.rs`）：

```rust
/// `offset` 是原始 UTF-8 字节偏移；`line` 和 `column` 都从 1 开始。
/// 列号按 Unicode 标量值计数，因此一个中文字符占一列。
pub offset: usize,   // 原始 UTF-8 字节偏移
pub line: usize,     // 一基行号
pub column: usize,   // 一基 Unicode 标量（码点）列号
```

**已核实**（LSP 规范）：

- **LSP 3.17 之前**：`Position` 的字符偏移**恒为 UTF-16 码元**；
- **3.17 起**：客户端用 `general.positionEncodings`（**按偏好降序**）声明支持的编码，
  服务端**必须从该列表里选**并在 `capabilities.positionEncoding` 回报，**不得覆盖**；
- **`utf-16` 是唯一强制支持的**；服务端不回报则**默认就是 UTF-16**；
- `utf-8` = 行内**字节**偏移；`utf-32` = 行内**码点**偏移。

**对照**：

| LSP 编码 | 主仓的对应字段 | 换算 |
| --- | --- | --- |
| `utf-32` | **`column`（码点计数）** | **直接对应** ✓ |
| `utf-8` | **`offset`（字节偏移）** | 需转成**行内**偏移 |
| `utf-16` | **无** | **必须换算** ✗ |

**结论**：

1. **UTF-16 换算跑不掉**——客户端可能只报 `["utf-16"]`；
2. **能在 `initialize` 里选 `utf-8`/`utf-32` 就选**，内部换算量最小；
3. **⚠️ 但不要假设客户端会给**。**VS Code 对 `utf-8` 的支持度本次未核实**
   （它历史上是 UTF-16-only），**主力目标如果是 VS Code，就按 UTF-16 是常态设计**；
4. **⚠️ 两份位置口径都要小心**：主仓 `line`/`column` 是 **1-based**，
   **LSP 是 0-based**。**每一条诊断、每一次跳转都要减一**——
   这是最容易写成 silent bug 的地方。

### 3.2 **高性能字符编码转换层**（本仓的核心基础设施）

**⚠️ 这是本仓性能的命门，必须当成一等公民设计，不能事后补。**

理由：

- **`textDocument/didChange` 是最高频的请求**——用户**每敲一个字符**都会触发；
- **每一次都要做位置换算**（LSP 位置 ↔ 主仓位置）；
- **主仓源码可以含中文、emoji、组合字符**，而主仓的源码位置口径
  （字节偏移 + 码点列）**与 UTF-16 都不相等**。

**设计要点**：

1. **必须建行首索引表**（每行的起始字节偏移）。
   否则每次 `(line, character) → offset` 都是 O(n) 扫描，
   **在大文件上会直接卡住输入**；
2. **索引表必须支持增量维护**——`didChange` 给的是**增量范围**，
   重建整表等于白做增量；
3. **换算必须是 O(log n) 或 O(1)**，不是 O(行内长度)；
4. **⚠️ 宽字符与代理对**：UTF-16 码元数 ≠ 码点数 ≠ 字节数，
   三者在含 emoji/CJK 的行上**互不相等**。**每一对换算都要有夹具**；
5. **⚠️ 组合字符**：`é` 可能是 1 个码点，也可能是 `e` + 组合符 2 个码点。
   主仓的口径是**码点**，**不是字素**——换算层要跟主仓口径一致，**不要自作主张按字素**。

**⚠️ 这条要单独立项**：它是**并发/性能敏感**的基础设施，
**不能被当成"工具函数"塞进某个 method 里**。

### 3.3 `xiao-core` 现在是「一问一答的子进程」，**不是长驻服务**

**已核实**（读过主仓协议层）：

- 通信是**子进程 + 8 字节大端长度前缀 + JSON 负载**；
- 请求类型：`hello`（含 `capabilities` 协商）、`run`、`test`、`build`、
  `package`、`environment`、`cancel`、`shutdown`；
- **主仓的 REPL 目前每次执行都新起一个核心进程**（主仓自己登记为债项）。

**⚠️ 对 LSP 的含义**：

- **LSP server 本身必须是长驻的**（这是 LSP 的模型），
  所以**要么**由 LSP 进程持有核心、**要么**每次请求起子进程（**后者在 `didChange` 频率下不可接受**）；
- **架构选型是本批最重要的待定项**（§4.1）；
- **⚠️ 主仓的 `run` 是「给我整份源码、还我整份结果」**，
  **没有增量接口**。LSP 的 `didChange` 是增量的，**这两者之间的落差要有明确的处理策略**
  （先全量重算？还是要求主仓提供增量？——**§4.4 待定**）。

### 3.4 主仓**目前缺** LSP 的核心能力（不是缺协议，是缺语义）

**已核实**（读过主仓的门禁与模块登记）：主仓**有**结构化诊断、
**有**稳定错误码、**有** `--json` 输出。**但**：

| LSP 需要的 | 主仓现状 |
| --- | --- |
| `publishDiagnostics` 的内容 | **有**（结构化诊断 + 稳定错误码）✓ |
| `textDocument/definition` | **无**——没有符号位置索引 |
| `textDocument/references` | **无** |
| `workspace/symbol` | **无** |
| `textDocument/documentSymbol` | **部分**（主仓的 `00D` 交接文档提过 AST 适配器协议与大纲） |
| `codeAction` 用的建议修复 | **无**——诊断里没有 `relatedInformation` / 建议编辑 |

**⚠️ 这意味着**：**索引层**（符号、引用）**大概率要在本仓建**，
但**索引的数据来源必须是主仓的分析结果**，不能自己扫源码猜（§2.1）。

**⚠️ 另一个已知的边界**：主仓已冻结 **`Declaration.end_line` 的真实语义**、
**大纲行数口径**（见主仓 `00D` 交接文档）——**引用位置信息时要用这一版口径**，
不要按直觉理解。

### 3.5 主仓的既有约定，本仓要沿用

- **诊断码是稳定的机器可读标识**（形如 `X01-SOURCE-004`、`X05-ENV-003`），
  **LSP 侧不要重新编号**，**原样透传**——用户和工具链都靠它对账；
- **协议字段"缺失不崩"**：主仓在 `metrics.peak_live_bytes` 上已确立
  「客户端不得因缺失该字段而崩溃」，**本仓消费主仓数据时沿用**；
- **主仓有文档门禁与规格向量**（`tests/spec/`）。本仓**要建自己的一套**，
  但**不要让两套门禁互相依赖**。

## 四、刻意留白，**待专项讨论决定**

**⚠️ 以下每一条都不许在实现里顺手定掉**——它们是本仓的架构级决策，
**要么专项讨论、要么显式登记为待定**。

### 4.1 架构：子进程 vs 库模式
LSP 直接**调用 `xiao-core` 子进程**（复用协议、隔离干净，但进程往返贵），
还是**链接主仓的 crate 做库模式**（快，但要主仓支持"库形态"，
且会**把主仓的内部类型变成跨仓契约**）？——**未定**。

### 4.2 索引策略
符号/引用索引放**内存**还是**持久化**？增量更新的粒度？
**未定**。

### 4.3 支持哪些 method、什么顺序
`publishDiagnostics` 显然最先（主仓已有内容），但**"先做哪些"要有明确理由**，
不要按 LSP 文档目录顺序抄。**未定**。

### 4.4 增量策略
`didChange` 的增量是 LSP 侧的事实，而主仓是整份输入。
**是 LSP 侧累积成全文再交给主仓，还是要求主仓支持增量？**——**未定**。
**⚠️ 若选后者，那是主仓的接口变更，要走主仓的冻结流程**（§2.1）。

### 4.5 与主仓的版本对齐
LSP 要跟主仓的**哪个版本**的语义走？主仓一次冻结变更后，
本仓如何知道要跟进？——**未定**。**但这关系到 §2.3 的"引用而非复制"能不能落地**。

## 五、开工前的最低要求

专项规划**至少**要先回答：

1. **§4.1 的架构选型**——它决定后面所有事的形态；
2. **§4.4 的增量策略**——它决定 §3.2 那个转换层的接口长什么样；
3. **第一批支持的 method 清单与退出条件**——照主仓的习惯，
   每个批次要有**可实测的退出条件**，不是"实现了就算"。

**⚠️ 最后一条提醒**：主仓在**终端侧**已经踩过的坑（`didChange` 级别的输入延迟、
位置换算的 silent bug、能力不可用时的静默降级），
**在 LSP 侧会以更尖锐的形式重演**——因为编辑器的输入频率远高于 REPL。
**§3.2 那个转换层不是"优化项"，是前置条件。**

## 六、启动时机与将来的同步规矩（**现在都不执行**）

> 这一节记的是**安排**，不是**任务**。**在触发条件出现之前，不要按它动手。**

### 6.1 启动时机：**等主仓开发完第一版**

**星崽 2026-09-28 定：LSP 在主仓完成第一版之后才搭建。**

在那之前：

- 本仓**不写实现**、不建 workspace、不选型；
- 本文**保持最新即可**——主仓的契约发生变更时，回来更新 §三 的「已核实」部分；
- **⚠️ 不要"趁早先把架子搭起来"**。主仓第一版之前的语义还在动，
  此时建的任何索引层/换算层都注定要返工。

**「第一版」的具体里程碑以主仓的阶段规划为准**，本文不越俎代庖定义它。

### 6.2 将来要立的规矩：**主仓改，同步改本仓**

**待主仓第一版完成后执行。**

> 主仓发生**会影响 LSP 的改动**时，**必须同步更新本仓文档**。

**⚠️ 这条规矩要立在主仓**——因为**触发方是主仓的改动**，本仓只是被同步的一方。
主仓侧应把它写进自己的文档约定或门禁里；**本仓单方面写没用**（主仓改的时候没人看这里）。

**「会影响 LSP」的初步判定**（待那时细化）：

- **位置模型**——`SourcePosition` 的口径（§3.1 整节都建立在它上面）；
- **诊断码与诊断结构**——§3.4 与 §3.5 依赖它；
- **进程协议**——请求/响应字段、能力协商（§3.3）；
- **模块与符号的可见性规则**——索引层的数据来源（§3.4）；
- **任何会让本文 §三 的「已核实」失效的改动**。

**⚠️ 这条比它看起来重要**：本仓的价值全建立在「主仓是唯一语义来源」（§2.1）之上。
**如果主仓改了而本仓不知道，本仓就会变成一个自信地输出过期语义的东西**——
那比没有 LSP 更糟。
